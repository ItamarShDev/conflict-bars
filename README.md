# ConflictBars

An interactive, bilingual timeline that places Israeli and Palestinian hip‑hop next to the conflicts it responds to. Built with Next.js (App Router), React 19, TypeScript and Tailwind CSS v4, with conflict and song data maintained in repository files.

## Project Goal

Document and visualize how the local hip‑hop scene intersects with conflicts and sociopolitical events. The timeline aims to:

- Give a chronological, two‑column view: conflicts on one side, songs and releases on the other.
- Offer neutral, sourced context — dates, lyric samples, links, and stated or reported political leanings.
- Work in English and Hebrew through locale‑aware routing.
- Let visitors submit songs or suggest corrections.

Entries should be concise, sourced, and neutral in tone. Eligibility rules and the data shape live in [AGENTS.md](./AGENTS.md) and [data/AGENTS.md](./data/AGENTS.md).

## Project Structure

- `data/<artist>/<era>.ts` — song records, the source of truth for songs (`90s.ts`, `2000s.ts`, `2010s.ts`, `2020s.ts`, plus an `index.ts` re‑export)
- `data/songs-generated.json` — build artifact produced from `data/`; git‑ignored, regenerated by `npm run generate-songs` (which `predev`/`prebuild` run automatically)
- `timeline/` — shared types (`types.ts`), conflict data (`conflicts.ts`, `conflict-utils.ts`), and the political‑leaning map (`artist-political-affiliation.ts`)
- `src/app/[lang]/` — the single locale‑aware route plus OG/Twitter images; `src/app/layout.tsx`, `globals.css`
- `src/components/timeline/` — `Timeline.tsx`, `YearSection.tsx`, `YearRail.tsx`, `SongEntry.tsx`, `FilterPanel.tsx`, `HelpModal.tsx`, `LanguageSwitcher.tsx`, `TimelineHeader.tsx`, `translations.ts` (en/he strings)
- `src/components/conflict/` — conflict card pieces; `src/components/SubmitSong*` — submission modal/form
- `src/utils/song-submission-mailto.ts` — browser-side prefilled email draft builder
- `src/utils/` — `file-songs.ts` (reads generated JSON), `timeline.ts` (merges conflicts + songs by year), `colors.ts`
- `convex/` and historical migration/sync scripts — retained for existing data; not used by the app runtime
- `scripts/` — `generate-songs-json.ts` and legacy migration/sync utilities

## Timeline Behaviour

`src/utils/timeline.ts` groups entries by year and the timeline renders the **union** of years that have a conflict and years that have a song, so a song from a year with no recorded conflict (e.g. 2003, 2019) still appears — its conflict column shows a neutral "no recorded conflict" note. Filters cover language, political leaning and conflict.

## Data Flow

```
data/<artist>/<era>.ts
  └─ scripts/generate-songs-json.ts   (recursively scans data/, skips index.ts)
       └─ data/songs-generated.json
            └─ src/utils/file-songs.ts → app/[lang]/page.tsx (server)
timeline/conflicts.ts ──────────────────┘
                                          └─ src/utils/timeline.ts → Timeline
```

Songs render from generated JSON and conflicts render from `timeline/conflicts.ts`. Song contributions and corrections are sent privately by email; the timeline remains file-backed. Because the generator walks the filesystem, adding or removing a song file changes the catalog — removing an artist means deleting their song files, not just their `index.ts` export.

## Content Model

### Song (file data)

```ts
{
  name: "Song Title (transliteration / translation)",
  artist: "Artist Name (native)",
  collaborators?: string[],
  language?: "Hebrew" | "Arabic" | "English" | "Hebrew/Arabic" | ...,
  published_date: "YYYY" | "YYYY-MM" | "YYYY-MM-DD",
  lyric_sample?: { hebrew?: string; english_translation?: string },
  full_lyrics?: { hebrew?: string; english_translation?: string },
  links?: { lyrics?: string; song_info?: string; youtube?: string },
}
```

`published_date` is parsed with `new Date()`, so decade placeholders like `"2020s"` do not render — always use a real year.

### Full lyrics

Song cards link directly to external lyrics through `links.lyrics`, including
compact cards. A song without a source shows **Lyrics link unavailable** instead
of an empty dialog. Keep only links to the matching song's lyrics (or an official
lyric video/description), not articles that merely quote excerpts.

For songs with supplied or licensed full text, a **Full lyrics** button shows
Hebrew and English in an on-site dialog. Store complete texts in `full_lyrics` on
the existing record in
`data/<artist>/<era>.ts`; use multiline template strings to preserve line breaks
and blank lines between verses. `predev` / `prebuild` include these fields in the
generated song catalog without a database migration.

Only add supplied or licensed complete lyrics and translations. Keep
`lyric_sample` for excerpts/context, and `links.lyrics` for the external source;
neither is treated as full lyrics. In the dialog, missing languages display an
explicit not-yet-added message, with the source link when available. No complete
lyrics have been copied into the catalog.

### Political leaning

`timeline/artist-political-affiliation.ts` maps the exact `artist` string to `{ era, affiliation, notes }`. The key must match the song's `artist` value verbatim, otherwise the entry falls back to the "unknown" grey border.

### Contributions

The bilingual contribution form opens the visitor's email app with a prefilled message to `itamarsharifytech@gmail.com`. New submissions and file-backed corrections include the proposed metadata, lyric samples, links, and the original entry details. The visitor must review and send the draft; the site does not send email or collect contact details. Oversized drafts are never shortened: the form shows the complete message and a copy fallback instead of opening a potentially truncated link.

## Internationalization

The locale is a route segment: `src/app/[lang]/` handles `en` and `he`, and `next.config.ts` redirects `/` to `/he`. UI strings live in `src/components/timeline/translations.ts` — add both `en` and `he`.
